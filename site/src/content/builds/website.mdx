<ShortVersion>
The first build is the site you're reading. Claude Code scaffolded an Astro
project where the whole site is driven by **one content collection** — home,
archive, each build log, and the tools index all read from the same markdown
files, so adding a build is adding one file, not editing four pages. That
architecture came together cleanly. The honest caveat: the part that ate the
most time had nothing to do with building — it was untangling a chain of Git and
GitHub auth mistakes, all of them mine.
</ShortVersion>

That claim is the whole architecture, so here it is as files — one content entry,
and the four page files that read it:

```
site/src/
├─ content.config.ts               the schema all four views validate against
├─ content/builds/website.mdx      ← the one entry (this post)
└─ pages/
   ├─ index.astro                  → home
   ├─ builds/index.astro           → archive
   ├─ builds/[slug].astro          → this build log
   └─ tools/index.astro            → tools index
```

Those four pages all read that same collection — none of it is bespoke to this
post, so you could lift this structure wholesale for your own site. (The standalone
pages — About, Privacy, the disclosure — are a separate `pages` collection; they
don't touch the build data at all.)

## The honest process

The site scaffold and the four page templates were the smooth part. Getting the
repository onto GitHub was not — and every snag traced back to my own setup, not
to Claude Code or GitHub. Tagged honestly:

<ProcessStep result="fail" title="Pushed over HTTPS with a password" tag="my-setup">
The first push used HTTPS with a plain account password. GitHub retired that path
for Git operations years ago — it needs a token or an SSH key. Dead on arrival.
</ProcessStep>

<ProcessStep result="fail" title="Registered the SSH key as a read-only deploy key" tag="my-setup">
Switching to SSH, I added the key as a repo **deploy key**. Those default to
read-only, so the handshake succeeded and the push was still denied. Recreating
the repo didn't help — the fix was never the repo, it was the key's scope.
</ProcessStep>

<ProcessStep result="fail" title="Wrong Git identity, and two keys in the agent" tag="my-setup">
The first commit landed under a leftover global `user.email` from another
project. On top of that, `ssh-add -l` showed the old and new keys both loaded, so
which one GitHub actually accepted was ambiguous — it kept authenticating through
the stale, read-only entry.
</ProcessStep>

<ProcessStep result="pass" title="What worked">
A repo-local Git identity (`git config --local`), a single account-level SSH key
(not a deploy key, so there's no read/write toggle to fight), and clearing the
agent down to just that one key. Clean first commit, correct author, full
scaffold pushed. Boring, but honest.
</ProcessStep>

**How this was actually made** — worth a note, because it's a technique you can
steal. The concept and the page designs didn't come from one AI in one pass. Most
of the thinking was done in Claude (Opus 4.8), with ChatGPT (5.6) pulled in as a
second opinion; the UI mockups were made by Claude, then critiqued by ChatGPT, with
the useful feedback folded back in by Claude. Having one model red-team another's
work caught things the first missed. Simple move, real payoff.

An honest correction, added later: this section used to promise "the full
back-and-forth, with the actual critiques and prompts" in the repro pack — and the
pack shipped without it, because none of it was ever captured **into the repo**.
The original chat histories may still exist outside it, so this is a capture
failure rather than a lost artifact, and it's recoverable. What won't happen is
reconstructing the exchange from memory and presenting it as the original:
a plausible-looking transcript written after the fact is a fabrication, however
accurate it feels. Capturing this material during the build is now an explicit
pipeline step, and the pack states exactly what it has and where it came from.

only version that's consistent with claiming "no database, no lock-in": a pack you

  drawn from the actual code, and why `/tools` is a projection rather than a second list.
- **`schema.md`** — the content schema annotated field by field, including the three

Alongside it, already public: [`build-notes.md`](https://github.com/jigg-ai/jigg/blob/main/builds/website/build-notes.md)
(the journal, dead ends included) and [`test.md`](https://github.com/jigg-ai/jigg/blob/main/builds/website/test.md)

## Postscript: making the newsletter signup stay on the page (2026-07-25)

Eight days after launch, one piece of the site still did the wrong thing: the
email signup **redirected to Buttondown's own page** instead of submitting inline.
Fixing that — "just subscribe and stay put" — became the longest debugging chase of
the whole build, and it ended on a cause that wasn't in the code at all: a Buttondown
spam-firewall setting that *our own testing had tripped*. If you're wiring a
newsletter into a JavaScript site, this is the section to read. The honest caveat up
front: the most instructive part is where I called it "fixed" on evidence that was
quietly wrong — twice.

<StatTiles variant="fact" stats={[
  { value: "Server-side", label: "the only path that works" },
  { value: "1 setting", label: "was the actual root cause" },
  { value: "2×", label: "I called it fixed too early" },
]} />

<ProcessStep result="fail" title="Shipped an inline version that was never actually tested" tag="my-setup">
The first attempt swapped the redirect for a hidden-iframe form post and showed an
inline "check your inbox." It passed local verification — except the local test had
the form pointed at a dummy page, so the one thing that mattered, a real cross-origin
POST to Buttondown, was never exercised. In production it failed silently: visitors
saw the success message and nobody got subscribed. "Verified locally" meant nothing,
because the test mocked away the exact thing that broke.
</ProcessStep>

<ProcessStep result="fail" title="Every browser-only path is a dead end" tag="tool-limit">
Three ways to submit straight from the browser, three walls: a direct `fetch` is
**CORS-blocked** by Buttondown's embed endpoint; a hidden-iframe submit gets
**stripped by browser tracking protection** (reliably fails in Safari); a `no-cors`
fetch reaches the server but creates nothing. No purely client-side method is
dependable — the embed endpoint just doesn't expose one.
</ProcessStep>

<ProcessStep result="pass" title="Move it server-side">
The architecture that stuck: a small Netlify Function calls Buttondown's authenticated
API server-side. The form posts same-origin — no CORS, no new tab — and gets real
success / already-subscribed / error states back. Correct design. It also, immediately,
returned an error on every single call.
</ProcessStep>

<ProcessStep result="fail" title="Called it fixed — twice — on evidence that was wrong" tag="my-setup">
The proxy 400'd every time. First wrong guess: forward the visitor's IP; a couple of
tests went green, so I declared it solved. Those greens came from `curl` running on my
own machine — a residential IP — not the datacenter path real users actually hit. A
clean isolation test killed the theory outright. When a result depends on *where the
request comes from*, a test that doesn't run from production's origin isn't a test —
it's a lie you tell yourself.
</ProcessStep>

<ProcessStep result="fail" title="The block was self-inflicted" tag="my-setup">
The real error, once I stopped guessing and read it: **"This subscriber was blocked by
your firewall."** Buttondown's *Attack mode* auto-escalates to IP-address auditing when
it detects a surge of unactivated subscribers — and our own burst of test signups *was*
that surge. It then audited the connection IP, which for a server-side proxy is always a
datacenter address → a permanent false positive against our own form. The tool's rough
edge here: it surfaced only as a bare `400`, with nothing pointing at a user-configurable
setting as the cause.
</ProcessStep>

<ProcessStep result="pass" title="The fix">
Three settings in Buttondown's Firewall: disable **IP-address auditing** and **Attack
mode**, and drop **Auditing mode** from Aggressive back to Enabled. Safe here because the
newsletter is double opt-in — nobody joins the list without clicking a confirmation link,
so *that*, not the IP audit, is the real spam gate. Verified from a real browser, and a
rapid burst of signups now all go through.
</ProcessStep>

The code that finally shipped is a few dozen lines. The lesson is the expensive part, and
it's the same one twice: I trusted a green result without checking that the *test* matched
production — first the mocked endpoint, then the residential IP. An AI pair-builder will
happily hand you a passing check; making sure the check exercises the real thing is still
the human's job.
